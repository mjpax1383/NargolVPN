# سقف پلتفرم‌های رایگان

اعداد زیر وضعیت پلتفرم‌ها در زمان نوشتن است. قبل از رشد جدی، صفحهٔ قیمت‌گذاری هر سرویس را یک‌بار چک کنید؛
اما طراحی پروژه به‌گونه‌ای است که حتی اگر یکی از این سقف‌ها نصف شود، کار متوقف نشود.

## Cloudflare Workers

| مورد | سقف رایگان | مصرف این پروژه |
| --- | --- | --- |
| درخواست | ۱۰۰٬۰۰۰ در روز | تایمر ۹۶ + خوانندگان ساب |
| CPU در هر فراخوانی | ۱۰ میلی‌ثانیه | چند میلی‌ثانیه |
| زیردرخواست (fetch) در هر فراخوانی | ۵۰ | حداکثر ۳ (تلگرام، گیت‌هاب، README) |
| Cron Trigger | ۳ عدد | ۱ عدد (`*/15 * * * *`) |
| حجم کد | ۳ مگابایت فشرده | کمتر از ۵۰ کیلوبایت |

**چرا ۱۰ms مهم است:** اگر درخواستی بیشتر مصرف کند، با خطای **1102** قطع می‌شود. به همین دلیل Worker هیچ‌وقت
منابع را جمع‌آوری یا پارس نمی‌کند؛ فقط چند کوئری D1 و یک fetch دارد.

**کش:** `/api/configs` در لبه با TTL ۶۰ ثانیه کش می‌شود. `/sub/*` عمداً edge-cache نمی‌شود
(کلید کش فقط URL است و همان آدرس باید بسته به User-Agent یک‌بار HTML و یک‌بار base64 بدهد)؛
فقط فایل base64 با `max-age=300` در مرورگر/کلاینت کش می‌شود.

## Cloudflare D1

| مورد | سقف رایگان | مصرف این پروژه |
| --- | --- | --- |
| فضای ذخیره‌سازی | ۵ گیگابایت | هر ۱۰۰٬۰۰۰ کانفیگ حدود ۵۰ مگابایت |
| ردیف خوانده‌شده | ۵٬۰۰۰٬۰۰۰ در روز | با کش لبه، کمتر از ۵۰٬۰۰۰ |
| ردیف نوشته‌شده | ۱۰۰٬۰۰۰ در روز | حدود ۲۵٬۰۰۰ |
| اندازهٔ کوئری | ۱ مگابایت | بسته‌های ۱۰۰تایی، هر کدام چند کیلوبایت |

**نکتهٔ کلیدی: D1 «ردیف نوشته‌شده» را برای هر ورودی ایندکس هم می‌شمارد.** یعنی یک upsert ساده در
`configs` که چهار ایندکس دارد، ۶ ردیف حساب می‌شود (خود ردیف + ایندکس کلید + ۴ ایندکس دیگر).

**محاسبهٔ قدیم (چیزی که سقف را پر کرد):** ۵۴۰ تست در ساعت × (۶ ردیف `configs` + ۳ ردیف `attempts`)
≈ ۴٬۸۰۰ ردیف در ساعت ≈ **۱۱۵٬۰۰۰ در روز** — یعنی بالای سقف ۱۰۰٬۰۰۰.

**محاسبهٔ جدید:**

- نتیجهٔ موفق → ۱ upsert در `configs` = **۳ ردیف** (خود ردیف + ایندکس کلید + `idx_configs_global`).
- نتیجهٔ ناموفق → فقط یک `UPDATE ... WHERE id = ?` که اگر ردیف نباشد **۰ ردیف** می‌نویسد.
  کانفیگی که هرگز کار نکرده اصلاً ذخیره نمی‌شود.
- هر انتشار ~۶۰ ردیف (۱۴ ساب + `top` + چند `meta`).

نتیجه: حدود ۹۰۰ ردیف در هر اجرا ≈ **۲۲٬۰۰۰ در روز**؛ یعنی ۴ تا ۵ برابر جا برای رشد.

**ایندکس‌ها:** فقط `idx_configs_global` می‌ماند (همان کوئری استخر زنده). سه ایندکس دیگر
(`score`، `ir`، `seen`) هیچ کوئری‌ای نداشتند و حذف شدند.

**کش seen تستر:** در ورک‌فلوی گیت‌هاب، پوشهٔ `tester/state` کش می‌شود تا کانفیگی که یک‌بار رد شده،
۳۶ ساعت دوباره تست نشود. قبلاً هر اجرا از صفر شروع می‌شد و همان کانفیگ‌های مرده هر ساعت دوباره
کشف و دوباره نوشته می‌شدند.

اگر باز هم به سقف نزدیک شدید:

- `MAX_NEW` را از ۲۸۰ کم کنید (مثلاً ۱۵۰).
- `prune` را بیشتر اجرا کنید (الان هر ساعت: اجراهای ۷ روز، کانفیگ‌های مرده‌ی ۲ ساعت).
- تست را به دو ساعت یک‌بار تغییر دهید (`DISPATCH_INTERVAL_MIN = "115"`).

## GitHub Actions

| مورد | سقف | یادداشت |
| --- | --- | --- |
| ریپوی **عمومی** | نامحدود | پیشنهادشده |
| ریپوی خصوصی | ۲۰۰۰ دقیقه در ماه | این پروژه ماهی ۱۵۰۰ تا ۲۵۰۰ دقیقه می‌برد → به سقف می‌خورد |
| حداکثر زمان هر Job | ۶ ساعت | `timeout-minutes: 40` گذاشته شده |
| ذخیره‌سازی کش | ۱۰ گیگابایت | کش Xray حدود ۱۵ مگابایت |
| اجرای همزمان | ۲۰ (عمومی) | `concurrency` جلوی اجرای موازی را می‌گیرد |

**خاموشی خودکار:** اگر ۶۰ روز هیچ فعالیتی در ریپو نباشد، GitHub ورک‌فلوی زمان‌بندی‌شده را غیرفعال می‌کند.
چون Worker هر ساعت `subs/*.txt` را کامیت می‌کند، ریپو همیشه فعال می‌ماند و این اتفاق نمی‌افتد.

## اگر همه‌چیز به سقف خورد

ترتیب کاهش بار:

1. `DISPATCH_INTERVAL_MIN` را بالا ببرید (ساعتی → دو ساعتی).
2. `MAX_NEW` و `MAX_RETEST` را کم کنید.
3. `POST_COOLDOWN_MIN` را بیشتر کنید (پیام کمتر).
4. ساب‌ها را روی دامنهٔ اختصاصی + کش Cloudflare ببرید.
5. در آخر: یک VPS ارزان (یا Oracle Free Tier) بگیرید و همان `tester/agent.py` را با cron روی آن اجرا کنید — کد تغییری نمی‌خواهد.

## چطور مصرف واقعی را ببینید

- Cloudflare Dashboard → Workers & Pages → vpnbot → Metrics (درخواست‌ها، خطاها، مدت اجرا)
- Cloudflare Dashboard → D1 → vpnbot → Metrics (ردیف‌های خوانده/نوشته)
- GitHub → Settings → Billing → Actions (دقایق مصرفی)
- `npx wrangler tail` برای دیدن خطاهای زنده
